Part 0The intuition

In this part: what this program does, what it is trying to win, and the one thing that nearly broke it.

What we HAVE

Anthropic sells three model sizes. Haiku is cheap, Sonnet is the middle, Opus is expensive. You pay per token, so the size you pick on each request is the size you pay for.

Most callers pick one model and use it for everything. That means simple requests — reformat this, translate that, count these — get billed at the price of hard ones.

claude-router puts a decision in front of every request. It reads the request, guesses how hard the task is, and sends it to the cheapest model that can do the job. It ships in two forms that share one engine:

  • a library — createRouter({apiKey}).send(params), a drop-in for the Anthropic SDK's messages.create;
  • a local HTTP proxy — you point ANTHROPIC_BASE_URL at 127.0.0.1:8787 and existing clients route with zero code changes.
The load-bearing fact Once the router chooses the model, it owns everything that depends on the model. Not just the price — also which parameters that model accepts, which tier a failure escalates to, and which baseline the savings are measured against. A caller that hands over model choice hands over all four. Nearly every design decision below follows from this one sentence.

What we WANT

The same answers, at a lower bill, with nothing changed on the caller's side — and an honest number telling you how much you saved. If the router silently made things worse, you should be able to see that in the logs.

What's IN THE WAY

The headline use case is Claude Code, and it is exactly the case where naive routing fails. Here is the sequence that actually happened, found during an end-to-end pass against the live API:

  1. Claude Code always pins a model in the request body, so it never routes — you must run the proxy with --force-route to override that.
  2. Every Claude Code request carries a large constant payload: a long system prompt, roughly 15 tool definitions, and prior turns full of tool output.
  3. The classifier scored the whole payload. Long system prompt: +10. Expert words in it: +15. Tools defined: +8. Many tools: +7. Tool blocks in flight: +10.
  4. That is a fixed +40 on a base of 35 — before the classifier reads one word of the user's actual question. The Opus threshold is 70.
  5. So every request tripped it. Including "what is 2+2?".
The user-visible damage A cost router that made things more expensive. Trivial turns went to Opus at $5/$25 per million tokens while the Sonnet baseline was $3/$15 — so savedCents came out negative and the log printed extra: $… instead of saved: $…. The one thing the product exists to do, it did backwards.

Part 1What you need to know first

In this part: six terms and one map — after this, nothing in the code will be unfamiliar.

Tier One of 'haiku' | 'sonnet' | 'opus'. Not a model ID — a slot that a model ID is looked up in. The whole system routes on tiers and resolves IDs at the last moment, which is why Bedrock and Vertex work with no extra branching.
Score A number 0–100 produced by the heuristic classifier. Under 30 → haiku, over 70 → opus, otherwise sonnet. Every weight that moves this number lives in one exported block, HEURISTIC_WEIGHTS, so tuning is one file.
Agentic session A request carrying tool definitions, or tool_use / tool_result blocks. Detected by isAgentic(). Coding-loop turns are floored at sonnet — a trivial-looking step in a loop can still be hard to execute.
Passthrough A request that bypasses routing entirely and is forwarded byte-for-byte to api.anthropic.com. Happens when the body pins a real model and --force-route is off. It is why the raw body is read as text, once.
RouteMeta / RouteEvent The receipt for one routed call: tier, model, tokens, cost, savings, whether it was retried. Two names for near-identical data — library vs proxy. They are never unified into one type; see Part 2.
Escalation Re-running a completed response one tier higher because it was cut off or was a refusal. Distinct from rate-limit fallback, which walks up for a completely different reason. Confusing the two is the bug in Part 4.

Part 2The idea of the design

In this part: the whole architecture in one sentence, and the rule that decides what gets shared.

The architecture, in one sentence One classifier turns a request into a tier, one kernel executes that tier (including every retry), and one fold turns finished calls into money — the library and the proxy are two thin callers of those three, and nothing else is allowed to re-implement them.

Why that's the right shape here:

  • The two front doors are genuinely different, but only at the edges. The library returns an object; the proxy returns an HTTP response. Their routing semantics must be identical. So the split is drawn exactly there: shared execution, separate presentation.
  • Duplication had already caused a real bug. Before route.ts existed, send() and handleNonStreaming each had their own retry loop, and the two had silently drifted on the escalation condition. Unifying them was a bug fix, not tidying.
  • Sharing is by behaviour, not by type. foldOutcome reads a five-field structural shape (RouteOutcomeLike), so RouteMeta and RouteEvent both satisfy it without either module adopting the other's record. The fold is shared; the records stay independent.
  • Tier-to-model resolution is deferred to the last moment. That single indirection is what lets Bedrock's us.anthropic.claude-opus-5-v1:0 and a plain claude-opus-5 flow through the same code and price the same — as does yesterday's claude-opus-4-8, which is what let the opus tier move to Opus 5 without touching the pricing table.

The key distinction: the two callers of the same kernel

The library and the proxy differ in exactly three settings. Everything else about how a route executes is identical, by construction.

Library (index.ts)Proxy (handler.ts)
Rate-limit 429 fallbackOnRateLimit: true — walks up the tiers and returns an answer false — the 429 surfaces to the client, which owns its own backoff
Where results go CostTracker, in memory, O(1) RouteEvent → capped array + append-only JSONL file
Client One client built from the config's API key One client per credential, from the request headers, LRU-cached at 100

The third row is not a detail. The proxy sees many callers' keys, so it cannot hold a single client — but rebuilding one per request would throw away HTTP keep-alive to the API on every call. An LRU keyed on the credential is the whole answer.

Part 3The twist

In this part: the subtlety that separates "score the request" from routing that actually saves money.

The naive classifier is the obvious one, and it is what shipped first: flatten the whole request to text, count complexity signals, add up weights, pick a tier. It scores well on isolated prompts. It fails completely on the product's main customer.

The reason is that an agentic client's request is mostly not the task. It is scaffolding: the harness's system prompt, its tool definitions, the tool output from previous steps. That scaffolding is nearly identical on every request in a session. A classifier that scores it is measuring the client, not the question.

Why that's poisonous A constant signal in a scoring function is not noise — it is a bias, and it points one way. The harness signals sum to about +40, always. Add the base of 35 and you are at 75, past the Opus threshold of 70, before reading the user's words. The classifier's discriminating signals — the verbs, the math, the code — could then only move the score within Opus territory. Routing became a constant function that returned opus, wearing the costume of a classifier.

The repair is three rules, and each one addresses a different way the constant leaks in. Removing any one of them leaves the bug partly alive.

The rule 1. Score the task, not the payload. Complexity signals are read from the latest user turn only — that is where the discriminating information lives.
2. Cap the scaffolding. The harness signals are summed and clamped to HARNESS_SIGNAL_CAP = 15. Base 35 + 15 = 50, which sits mid-Sonnet. The harness can nudge a borderline call upward; it can never on its own reach Opus.
3. Floor agentic sessions at sonnet. With tools present, haiku is off the table by default — a trivial-looking step inside a coding loop can be hard to execute, and a wrong cheap step cascades into more turns, which costs more than the step saved.

Rules 2 and 3 look like they conflict, and that tension is the thing worth understanding. Rule 2 says the harness must not push you up. Rule 3 says the harness must stop you going down. Both are true because they answer different questions. Rule 2 is about difficulty: the presence of tools tells you nothing about how hard this turn is. Rule 3 is about the cost of being wrong: inside a loop, a bad cheap answer is not cheap, because the loop pays for it again. Difficulty and blast radius are separate axes, and the scoring function is only allowed to model the first one.

One more constant leaks in through a side door: prompt length. Tool output can be enormous, so extraChars — the character volume inside tool_result blocks — counts toward the token estimate but is deliberately not fed to keyword matching. Big tool output means "big context", not "hard question".

Part 4The details: reading the code

In this part: five blocks of shipped code — the score, the floor, the kernel, the parameters, and the money.

1 · Scoring the task, and capping the harness

// src/classifier.ts — heuristicScoreDetailed
const taskText = extractLatestUserText(input.messages);  // ← Part-3 rule 1
let score = W.BASE;                                       // 35, mid-Sonnet

score += countMatches(taskText, SIMPLE_RE)  * W.SIMPLE_VERB;   // −12 each
score += countMatches(taskText, MEDIUM_RE)  * W.MEDIUM_VERB;   // +5
score += countMatches(taskText, COMPLEX_RE) * W.COMPLEX_VERB;  // +15

// --- Harness / scaffolding signals (CAPPED) ---
let harness = 0;
if (toolBlockCount > 0)      harness += W.TOOL_BLOCKS_PRESENT;  // +10
if (toolCount > 0)           harness += W.TOOLS_DEFINED;        // +8
if (toolCount > 8)           harness += W.MANY_TOOLS;          // +7
if (systemText.length > 500) harness += W.LONG_SYSTEM;         // +10
if (expertHits > 0)          harness += W.EXPERT_SYSTEM;       // +15
score += Math.min(harness, HARNESS_SIGNAL_CAP);      // ← 50 max, never Opus

Plain English: difficulty is measured only on what the user just said; everything the harness contributes is summed to at most 15, so 35 + 15 = 50 and the scaffolding alone can never reach the Opus threshold of 70.

Two ordering constraints hide in that block. taskText must be extracted before any keyword matching, or the harness's own words ("expert", "comprehensive", "analyze") count as task signal. And the cap must be applied to the sum, not to each term — capping each signal individually would still let five of them add up to 40.

Note also that the image signal is deliberately outside the cap. An image block is a genuine task signal — the request needs vision — not scaffolding.

2 · The agentic floor

// src/classifier.ts — applied to EVERY classification method
function applyAgenticFloor(result, input, opts) {
  if (result.tier !== 'haiku' || opts?.allowHaikuInAgentic || !isAgentic(input)) {
    return result;                       // ← no-op unless all three hold
  }
  const score = Math.max(result.score, opts?.haikuMax ?? 30);
  return { ...result, tier: 'sonnet', score, floored: true };
}

export async function classify(client, input, mode, haikuModel, opts) {
  const result = await (mode === 'heuristic' || !client
    ? classifyHeuristic(input, opts)
    : mode === 'ai' ? classifyAICached(...) : classifyHybrid(...));
  return applyAgenticFloor(result, input, opts);   // ← after ALL methods
}

Plain English: if tools are in play and any classifier said haiku, promote it to sonnet — and record floored: true so the decision is visible rather than silent.

The placement matters more than the body. The floor sits in classify(), the single unified entry point, after the method switch — so it applies to heuristic, AI, and hybrid alike. Put it inside classifyHeuristic and the AI path would quietly keep routing coding turns to haiku.

3 · The execution kernel

// src/route.ts — the one retry loop in the codebase
for (let i = startIndex; i < TIER_ORDER.length; i++) {
  const tier = TIER_ORDER[i]!;
  const fallbackUsed = i !== startIndex;      // we already walked up

  try {
    const response = await client.messages.create(
      normalizeParamsForTier({ ...apiParams, model: models[tier] }, tier),
      opts.requestOptions,
    );

    const decision = shouldRetry(response, tier);
    if (decision.retry && !fallbackUsed) {   // ← escalate ONCE, and only
      const escalated = nextTier(tier);       //   from the classified tier
      /* … one re-run at `escalated`, then return … */
    }
    return { response, tier, model, fallbackUsed, retried: false, ... };

  } catch (err) {
    if (opts.fallbackOnRateLimit &&
        err instanceof Anthropic.RateLimitError &&
        i < TIER_ORDER.length - 1) continue;   // walk up a tier
    throw err;
  }
}

Plain English: try the chosen tier; on a rate limit walk up the ladder (library only); if the answer comes back truncated or refusing, re-run it one tier higher — but only if this was still the tier the classifier originally picked.

!fallbackUsed is the load-bearing condition. Two different mechanisms can move you up the ladder, and they must not compose. A rate-limit walk-up has already spent a tier upgrade you did not ask for; letting a truncation escalation stack on top means one request could burn haiku, then sonnet, then opus, and bill you for all three. The rule is: at most one deliberate escalation, from the tier the classifier chose.

This loop is also why streaming does not retry. Once bytes are on the wire the client has already seen the beginning of the answer; you cannot un-send it and try again at a higher tier. handleStreaming therefore calls messages.stream directly and only sets the headers it knows before the stream finishes — tier, model, classifier, confidence, but not cost.

4 · Reconciling parameters with the routed model

// src/params.ts — applied before EVERY routed create/stream, retries included
if (tier === 'haiku') {
  if ('thinking' in out) delete out['thinking'];  // Haiku 4.5: no adaptive
  if (out['output_config']) { /* strip .effort, drop if now empty */ }
} else {
  delete out['temperature']; delete out['top_p']; delete out['top_k'];
  if (thinking?.type === 'enabled') {
    out['thinking'] = { type: 'adaptive' };  // Sonnet 5 / Opus 5 form
  } else if (thinking?.type === 'disabled' && !acceptsDisabledThinking(tier, out)) {
    delete out['thinking'];              // Opus 5 above 'high' effort; Fable always
  }
}

Plain English: the router changed the model, so it also has to fix up the parameters that model would reject — otherwise the request 400s purely because it was routed.

This is the load-bearing fact from Part 0 made executable. Claude Code sends adaptive thinking plus an effort setting; Haiku 4.5 rejects both. Without this function, --force-route would fail on every request that landed on haiku — not with a routing error, but with a confusing upstream 400. And note what it does not touch: messages, system, tools, max_tokens. Rewriting any of those would change what the user asked for, which is beyond a router's mandate.

The second branch is the same idea arriving from a different direction, and it shows why this function is permanent rather than a one-off patch. When the opus tier was promoted from Opus 4.8 to Opus 5, the models' rules diverged: Opus 4.8 accepted thinking: {type: 'disabled'} at any effort, Opus 5 accepts it only at high or below. Nothing about the router changed — a request that worked yesterday would 400 today purely because the tier now resolves to a different model. Tier indirection creates this obligation. The moment you decide the model on the user's behalf, you own every parameter that model rejects, including the ones it started rejecting after you shipped.

Note which parameter gets dropped when the two conflict. The request asks for no thinking and for xhigh effort; only one of them can survive. The router drops the thinking parameter and keeps the effort, because thinking depth is the model's own judgement call — the models that reject disabled all default to adaptive, so omitting it is the closest legal version of the request — while effort is a deliberate cost-and-quality choice the caller made. Quietly downgrading xhigh to high would be the router editing the user's intent rather than reconciling it.

5 · Turning a response into money

// src/models.ts — one pricing path for both callers
export function priceForModel(model, pricing) {
  if (pricing[model]) return pricing[model];        // user override wins
  const fam = familyForModel(model);                // 'opus' from any ID
  return fam ? (pricing[DEFAULT_MODELS[fam]] ?? FAMILY_PRICING[fam]) : undefined;
}

const cacheCost =
  (cache?.readTokens ?? 0)     * p.input * CACHE_READ_RATE +   // 10%
  (cache?.creationTokens ?? 0) * p.input * CACHE_WRITE_RATE;  // 125%

// src/totals.ts — the one fold, used by three sinks
export function foldOutcome(acc: RouteTotals, e: RouteOutcomeLike): void {
  acc.requests++;
  acc.costCents  += e.costCents;
  acc.savedCents += e.savedCents;                // baseline − actual; can be < 0
  if (e.retried) acc.retried++;
  acc.tiers[e.tier] = (acc.tiers[e.tier] ?? 0) + 1;
  /* … plus a per-day bucket keyed off the ISO timestamp … */
}

Plain English: price by model family so any dated or cloud-provider ID still prices correctly, count prompt-cache tokens at their real rates, and fold every finished call through one function no matter which of the three places is doing the counting.

Two traps are closed here. First, pricing is resolved by family, not by exact ID — so a new dated snapshot, or Bedrock's us.anthropic.claude-sonnet-5-v1:0, prices right with no code change, while an explicit user override still wins because it is checked first. Second, prompt-cache tokens are billed at 10% (reads) and 125% (writes) of the input rate. Claude Code caches heavily; omitting those tokens understates every cost figure the tool reports.

The three sinks differ only in when they fold. CostTracker folds one event at a time and keeps O(1) memory — no per-call array. history.ts folds newly appended JSONL lines behind an offset cache, because the file is append-only and a prefix once folded never needs re-reading. The dashboard reduces the live capped array on each render. Same arithmetic, three execution models.

The tests that lock this down

Tests use node:test with no external framework. The router tests replace the _client property directly, so classification and routing are exercised with zero network calls.

  • Arrange — build a request that looks like Claude Code: long system prompt, ~15 tool definitions, tool blocks in prior turns, and a trivial final user turn.
  • Act — classify it.
  • Assert — the tier is sonnet, not opus. On the unpatched classifier this same test produces opus, reproducing the exact production symptom rather than a proxy for it.

Beyond unit tests, a few suites bind an ephemeral loopback port (serve({port: 0})) to exercise the proxy over a real socket — daemon.test.ts for health polling and integration.test.ts end-to-end against a fake in-process upstream. Nothing reaches the public internet by default; the two passthrough tests that genuinely call api.anthropic.com are skipped unless RUN_NETWORK_TESTS=1.

What we deliberately did NOT touch

  • The request's meaning. normalizeParamsForTier only edits model-coupled parameters. Messages, system, tools, and max_tokens pass through unchanged.
  • The passthrough body. It is read once as text and forwarded verbatim, so a non-routed request is byte-identical to what the client sent. Only content-encoding and content-length are stripped on the way back, because fetch already decompressed.
  • The default bind address. 127.0.0.1. With Bedrock or Vertex the proxy uses the operator's cloud credentials and does not authenticate incoming requests — the loopback bind is the security boundary, not a convenience.
  • Streaming retries. Deliberately absent, per Part 4 block 3.
  • Throwing from the classifier. The AI path has a 1.5s timeout and a catch-all that falls back to the heuristic. A Haiku outage degrades routing quality; it never breaks a request.

Part 5Mini-glossary

Only the terms used above, in plain words.

Tier One of haiku, sonnet, opus. A slot, not a model ID — the ID is looked up per provider at the moment of the call.
Hybrid classifier The default mode. Runs the fast heuristic first, and only asks Haiku for a second opinion when the score is ambiguous (40–60 by default) or when the text produced no keyword signals at all — which is what non-English prompts look like.
HARNESS_SIGNAL_CAP The value 15. The ceiling on how much a client's constant scaffolding — system prompt, tool definitions, in-flight tool blocks — may contribute to the complexity score.
Agentic floor The rule that a tool-using session never routes to haiku. Opt out with routing.allowHaikuInAgentic.
Rate-limit fallback Walking up to the next tier when the API returns 429. Enabled in the library, disabled in the proxy — where the 429 is passed to the client instead.
Escalation retry Re-running a response one tier higher because it hit max_tokens with real output, or because it was a short refusal. Happens at most once, and never after a rate-limit walk-up.
savedCents Baseline cost minus actual cost, where the baseline is the configured default model (sonnet unless overridden). It can be negative — and when the Part-3 bug was live, it usually was.
--force-route Ignore the model pinned in the request body and route anyway. Required for Claude Code, which always names a model, and therefore the flag that exposed the Part-3 bug.
RouteOutcomeLike The five-field shape foldOutcome reads. Both RouteMeta and RouteEvent match it structurally, so the aggregation is shared without either module adopting the other's type.

Part 6Defend it

In this part: test yourself first, then the answers you'd give under pressure.

Check yourself

Why does capping the harness signals fix over-routing when lowering them would not? Lowering a constant just moves the constant. The signals are near-identical on every request in an agentic session, so whatever value they take, they shift the entire distribution by that amount rather than discriminating between requests. A cap bounds the shift: base 35 plus at most 15 is 50, which is inside the Sonnet band, so the scaffolding can influence a borderline call but can never on its own cross the Opus threshold at 70.
Rule 2 says the harness must not raise the tier. Rule 3 says the harness must raise the floor. Why isn't that a contradiction? They model different things. Rule 2 is about difficulty — the presence of tools says nothing about how hard this particular turn is. Rule 3 is about the cost of being wrong — inside a coding loop, a bad cheap answer is not cheap, because the loop pays for it again in extra turns. The score models difficulty only; the floor is a separate risk policy applied afterwards.
Why must escalation be blocked after a rate-limit walk-up? Because both mechanisms move you up the same ladder, and they would compose. A walk-up has already consumed a tier upgrade nobody asked for; stacking a truncation escalation on top could burn haiku, sonnet, and opus on a single request and bill for all three. The !fallbackUsed guard enforces at most one deliberate escalation, from the tier the classifier actually picked.
Why is pricing resolved by family rather than by exact model ID? Because exact IDs multiply and drift. Dated snapshots, Bedrock's us.anthropic.* inference profiles, and Vertex IDs all name the same underlying model at the same price. Family resolution means a new snapshot prices correctly with no code change. An exact-ID lookup is still tried first, so an explicit user override always wins.
Why does the proxy cache SDK clients per credential instead of building one per request? It serves many callers' keys, so a single shared client is impossible. But a fresh client per request discards the keep-alive connection to the API every time, adding a TLS handshake to every call. An LRU of 100 keyed on the credential preserves the connection pool without holding unbounded state.
Why does the streaming path not retry, and what does it give up? Once the first bytes reach the client, the response cannot be withdrawn — there is nothing to escalate from. It gives up truncation and refusal recovery on streamed calls, and it means the streaming response can only carry headers known before the call finishes: tier, model, classifier, confidence, but not cost or savings.

Likely challenges

"A keyword-weight heuristic is crude. Why not just always ask a model?" Cost and latency — the two things the project exists to protect. An AI classification is an extra API call on every request, so it must earn its place. Hybrid mode spends it only where the heuristic is genuinely uncertain: inside the 40–60 band, or when the text produced zero keyword hits, which is the non-English case the keyword lists structurally cannot score. Genuine AI verdicts are LRU-cached on a SHA-1 of the full normalized text; heuristic fallbacks are not cached, so a transient Haiku outage cannot pin a bad tier in the cache.
"The agentic floor throws away your biggest savings opportunity. Coding assistants are exactly where the cheap turns are." It is a default, not a law — routing.allowHaikuInAgentic turns it off. The default is set by expected cost, not sticker cost: a wrong haiku step in a loop is re-tried, re-prompted, and re-tooled, and those extra turns cost more than the one saved. Outside a loop, a bad cheap answer costs one retry, so haiku stays available there. And the floor is recorded as floored: true, so anyone can see when it fired and measure the tradeoff rather than argue it.
"Why not unify RouteMeta and RouteEvent into one record instead of a structural shape?" They serve different consumers and have genuinely different fields — RouteMeta carries classifier timing and is attached to the returned message; RouteEvent carries a timestamp and a 'passthrough' tier the library has no concept of. Unifying them would force each module to carry the other's concerns. What actually needed sharing was the arithmetic, not the record, so foldOutcome reads a five-field structural shape both already satisfy. Share behaviour, not types.
"Isn't a local HTTP proxy holding cloud credentials a security problem?" It would be if it were reachable. It binds 127.0.0.1 by default and that is documented as a security boundary rather than a default to tune: with the Bedrock or Vertex providers the proxy authenticates upstream with the operator's cloud credentials and performs no authentication of incoming requests. Binding it to a routable interface would expose those credentials to anything that can reach the port. On the Anthropic provider the caller's own key is still required and is what the per-credential client cache is keyed on.
"How do you know the fix works, rather than that the test was written to pass?" Three layers. The regression test reproduces the production symptom exactly — a Claude Code-shaped request with a trivial final turn routes to opus on the unpatched classifier and sonnet on the patched one. Integration tests exercise the proxy over a real loopback socket against an in-process upstream. And the fix was verified against the live API: trivial Claude Code turns landed on Sonnet where they had been landing on Opus, and a genuine "architect this and prove it correct" prompt still reached Opus — confirming the classifier still discriminates rather than having merely been clamped downward.
